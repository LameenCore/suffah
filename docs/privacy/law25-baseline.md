## Scope

Suffa processes **personal information about minors** (children ~10–13) and their
guardians, in Quebec, for education. Law 25 — not the GDPR, not PIPEDA alone — is
the governing regime. The data inventory and cross-border analysis live in
`docs/data-map.md`; this file covers the **governance** obligations: a person
responsible, consent, individuals' rights, retention, and breach response.

## 1. Person responsible for the protection of personal information

Law 25 requires a designated person responsible (the "privacy officer"); by
default it is the person with the highest authority in the organization, who may
delegate in writing.

| Field | Value |

## 2. Consent

**Standard:** consent must be *manifest, free, and enlightened*, and *given for
specific purposes*. Silence or a pre-ticked box is not consent. For a minor under
14, consent is given by the person having parental authority. (verify with counsel)

**How Suffa meets it (T37):**

- A **child account is inert until a guardian consent record exists** with
  `granted = true` for the current consent version. No lessons, no results, no
  playground access before that.
- The consent screen names **specific purposes**, each of which the guardian can
  see before agreeing:
  1. Delivering the curriculum and recording the child's progress.
  2. **AI-assisted instruction** — lessons, checkpoints, and assessments are
     generated by a third-party model (Anthropic); most calls carry only course
     text, one (the volunteer handoff briefing) carries the child's first name
     and progress signals.
  3. Using results to **assemble the progress/evaluation record** a family needs
     for Quebec home instruction (the family files it, not Suffa).
  4. **Retention** for the stated period.
- Consent is **versioned** (`consent_version`, e.g. `2026-09`). A material change
  to any purpose bumps the version and re-prompts the guardian; the old record
  does not carry the new purpose.
- Consent is **withdrawable**. Withdrawal is a new append-only row
  (`granted = false`), not a deletion of history. The UI explains the effect:
  withdrawing consent to AI instruction or to compliance assembly disables those
  features, and where that makes the service unusable we help the family close
  the account.
- Stored in `consent_records` (migration `0011`), append-only, one row per
  decision, with a hash of the consent copy shown for provenance.

**Gap / TODO:** guardian **identity verification** is out of scope for the demo
(any signup can select "parent"). A real deployment needs the masjid to vet the
guardian relationship — a status field + an admin check, not self-assertion.
(verify with counsel)

## 3. Rights of the individuals concerned

Law 25 gives individuals (here: the guardian on the child's behalf, and each
adult user for their own data) these rights. Suffa's commitment and current
mechanism:

| Right | Commitment | Mechanism today | Gap |
|---|---|---|---|
| **Access** — a copy of the personal information held | Respond within 30 days | Manual: the privacy officer runs an export query per family | Self-serve export UI — **T36 "done when" item still open**, tracked below |
| **Rectification** — correct inaccurate information | Correct promptly | Admin edits the `users` / results rows | — |
| **Withdrawal of consent** | Always available; effect explained | `consent_records` withdrawal row (T37) | — |
| **Erasure / de-indexing** | Delete on request except where a law requires retention | Manual: cascade delete from `users`; `pod_session_notes` / `pod_barakah_log` free-text scrubbed | Scripted erasure flow — open |
| **Portability** — a machine-readable copy of the computerized data the person provided | Provide the child's learning record as JSON/CSV | Not built | Open — same export path as Access |
| **Right to be informed of automated decision-making** | Disclosed | `/privacy` + consent screen name the AI processing; grading is deterministic code, not the model, and is described as such | — |

**Open build items for full T36 compliance:**

- [ ] **Self-serve data export** — one action that returns *all* of a family's
      data (account, family link, pod, every result, compliance reports, consent
      records, any session note that names the child) in a machine-readable
      bundle. Same query serves Access and Portability.
- [ ] **Right-to-erasure request flow** — an in-app request that opens a tracked
      task for the privacy officer, plus a script that performs the deletion and
      scrubs free-text mentions, with a record that it was done and what was
      legally retained.

These are recorded here rather than silently dropped; they are the remaining
distance between "we have a baseline" and "a family can rely on it".

## 4. Retention

Law 25: keep personal information only as long as needed for the purpose it was
collected for, then destroy or anonymize it.

| Data | Retention | Basis |
|---|---|---|
| Account (`users`) | While enrolled + a defined period after last activity — **operator-set, suggested one school year** | Needed to run the service; a short tail lets a family return without re-entry |
| Learning results | Same as account, **or** longer if the family asks us to hold the compliance record | The record's whole purpose is the home-instruction filing |
| `pod_session_notes`, `pod_barakah_log` (free-text that can name a child) | **Shorter** — suggested one term past the pod's last activity | Highest-sensitivity, lowest long-term value; called out in `docs/data-map.md` |
| `compliance_reports` | While the family wants it retained; otherwise with the account | Assembled academic record |
| `consent_records` | As long as legally required to evidence consent | It is the proof the processing was lawful |
| `audit_log` | Retained; ids + action names only, minimal PII | Security / accountability record |

The exact numbers are an **operator decision** — this table gives defensible
defaults. Once set, they go in `/privacy` (currently phrased as "to be set with
the operator") and become a scheduled cleanup job. (verify with counsel)

## 5. Cross-border transfer

Covered in full in `docs/data-map.md` §"Cross-border flows". Summary for this
baseline:

- Before communicating personal information outside Quebec, Law 25 requires a
  **privacy impact assessment** weighing the sensitivity, the purpose, the
  protections (contractual and technical), and the legal regime of the
  destination. (verify with counsel)
- Suffa has **one deliberate cross-border flow**: the Anthropic API (US). Most
  calls carry near-zero personal information. The **continuity briefing** call is
  the sensitive one — it currently sends a child's first name + pass/fail/attempt
  counts + recent session-note text.
- **Required before a real pilot:** (a) move the database from AWS `us-west-2` to
  `ca-central-1` (**T39**); (b) pseudonymize students to "Student A/B/C" in the
  briefing prompt and map back in-app; (c) a data-processing agreement with
  Anthropic, ideally zero-retention; (d) the PIA covering (b)/(c).

## 6. Breach response (confidentiality incident)

Law 25 process for a *confidentiality incident* (unauthorized access, use,
disclosure, or loss of personal information):

1. **Contain** — stop the incident, revoke exposed credentials, close the hole at
   the root (project convention: fix bugs at the root immediately).
2. **Assess risk of serious injury** — considering the sensitivity of the
   information (minors' education data ranks high), the likely consequences, and
   the likelihood of misuse.
3. **If there is a risk of serious injury:** notify the **CAI** and each affected
   individual (the guardian) **with diligence** — describe the information
   involved, the circumstances, what we've done, and what the person can do to
   reduce their risk.
4. **Record every incident** in a **register of confidentiality incidents**, kept
   for at least 5 years, whether or not it met the notification threshold. The
   register lives with the operator's governance records; a template is an open
   item.
5. **Remediate** — steps to prevent recurrence; note them in the register and, if
   code-related, in the progress journal.

| Field | Value |
|---|---|
| Who runs this | The privacy officer (§1), with the technical lead |
| Notification trigger | Risk of *serious* injury — assessed per incident, documented |
| Register location | Operator governance records — **[template TODO]** |
| Register retention | ≥ 5 years (verify with counsel) |
| Regulator | Commission d'accès à l'information du Québec |

**Current technical posture** (from the security audit, `docs/review/`):

- Tenant isolation is enforced in application code (`lib/db/*-queries.ts` take
  `masjidId` first); **database-level RLS is T31** — the main open
  defence-in-depth gap.
- `audit_log` (migration `0010`) is append-only and records sensitive admin
  actions.
- AI endpoints have rate limiting + model-call logging (T34).
- Passwords are hashed by Supabase Auth; the app never handles them.
- Backups: Supabase PITR + `docs/ops/backup-restore.md` + `npm run check:integrity`.
